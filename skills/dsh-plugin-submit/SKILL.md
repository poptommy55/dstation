# 分发 DSH 插件（投稿 或 导出）

用户说一句「帮我把 xxx 插件投稿」或「帮我把 xxx 导出给朋友」，剩下的交给工具。
**你负责选对通道、收集信息、运行一条命令、把结果翻译成人话。**

---

## 零、先选通道

| 用户想要 | 走哪条 | 结果 |
|---|---|---|
| 「上架」「让别人在市场里能搜到」「投稿」 | **投稿** | 进待审队列；人工审核通过后出现在 https://your-market-host/plugins/ |
| 「发给朋友」「给同事用」「做个安装包」「分享」 | **导出** | 产出一个 zip，对方解压双击就装好；不经过市场，不需要审核 |

两条可以都做：先导出给朋友用，再投稿上架。
**拿不准就问一句**：「你是想上架到市场，还是直接打包发给别人？」

---

## 一、铁律（先看这三条）

1. **上架信息必须问用户，不许自己编。**
   署名（`--author`）和一句话简介（`--summary`）会**公开显示**在市场页面上。
   你可以**提议**（比如从 `package.json` 的 description 拟一个），但必须让用户确认。

2. **绝不运行被投稿插件的代码。**
   不 `npm install`、不 `node index.js`、不执行它的任何脚本。只读文本。

3. **服务器会独立再检查一遍。**
   本地检查通过 ≠ 一定收下。服务器有自己的闸门（版本冲突、风险阻断项、限流）。
   本地检查只是为了**省一次网络往返**，不是权威。

---

## 二、标准流程

### 第 1 步：确定投哪个插件

用户没指明就问清楚。插件目录的特征：**含 `package.json`，且里面有 `dsh` 字段**
（`dsh.bundle` 或 `dsh.client`）。

常见位置：用户的工作目录、`%DSH_HOME%\plugins\<名字>\`、某个源码仓库。

⚠️ 如果用户指的是 `%DSH_HOME%\plugins\<名字>\`，注意那可能是**安装产物**而不是源码。
投安装产物通常也可以（内容一样），但要提醒用户：**改源码后要重新投稿**。

### 第 2 步：看一眼插件，准备好提议

读 `package.json`，拿到：
- `name` / `version`（工具会校验格式）
- `description`（可以据此拟 `--summary`）
- `license`

然后**向用户确认四件事**：

| 参数 | 怎么问 |
|---|---|
| `--author` | 署名写什么？（会显示在市场上，可以是昵称） |
| `--category` | 分类选哪个？只能是：**外观 / 效率 / 集成 / 开发 / 数据 / 其他** |
| `--summary` | 一句话简介（建议 ≤ 40 字，卡片上就显示这个） |
| `--contact`（可选） | 留个联系方式吗？出问题时方便找你 |

`--author` / `--contact` / `--homepage` / `--license` 会被记到
`%DSH_HOME%\plugin-author.json`，**下次投稿不用再填**。所以第一次填完之后，
后续可以只问分类和简介。

### 第 3 步：运行投稿

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8   # 不设中文会乱码
node "$env:DSH_HOME\skills\dsh-plugin-submit\tools\submit.mjs" `
     "<插件目录>" `
     --author "<署名>" `
     --category "<分类>" `
     --summary "<简介>"
```

工具会依次做：结构检查 → 风险扫描 → 打包 → 投递 → 打印回执。全程约 5 秒。

**想先看看会发生什么、不真的发出去**，加 `--dry-run`：它只生成投稿包落在当前目录。

### 第 4 步：把结果翻译给用户

**成功**（退出码 0）：
> 投稿成功，编号 `20260915-183100-51ce9ffd`，已进入待审队列。
> 机器初审：干净，风险分 100/100。
> 人工审核通过后会自动出现在 https://your-market-host/plugins/

**失败**：见下面的对照表。

---

## 三、失败对照表

工具的输出已经写成人话了，照着转述并**给出下一步动作**：

| 输出里出现 | 意思是 | 你该做什么 |
|---|---|---|
| `结构检查未通过` + 列出的条目 | 插件本身不完整（缺 `exports["./client"]`、缺文件…） | 逐条解释，帮用户改 `package.json`。**这个闸门防的是「装上去让 DSH 起不来」**，不能绕过 |
| `风险扫描发现阻断项` | 有 `eval` / 子进程 / `postinstall` / 二进制 / 混淆代码 | 解释**为什么**危险（报告里每条都有理由），帮用户改。**不要试图绕过** |
| `HTTP 409` + `线上已有 X.Y.Z` | 版本号没涨 | 让用户改 `package.json` 的 `version`（例如 `1.0.1` → `1.0.2`），再投一次 |
| `HTTP 409` + `已经在待审队列里` | 同版本重复投 | 不用重投。等审核，或改版本号 |
| `HTTP 429` | 投稿太频繁（每 IP 每小时 6 次） | 等一会儿再投 |
| `HTTP 503` + `待审队列已满` | 积压太多 | 告诉用户过几天再投，并**提醒管理员**去清理 |
| `无法连接投稿服务器` | 网络问题 | 建议用 `--dry-run` 先生成包，或检查网络 |

⚠️ **如果用户想「绕过检查」**：不要做。风险扫描的阻断项对应的是
「插件会被装进别人的机器，而 DSH 插件没有沙箱」。解释这一点，然后帮他改。

## 四、导出成「发给朋友就能装」的安装包

用户说「发给朋友」「给同事用」「做个安装包」时走这条。

### 两条路，先问一句

| 走哪条 | 什么时候用 |
|---|---|
| **界面按钮**（推荐） | 插件已经装在本机 → 让用户去「设置 → 插件 → D-STATION 市场 → 已安装」，点那行的**「导出」** |
| **命令行**（下面这条） | 插件还没装、在任意源码目录里；或者用户就要你直接产出文件 |

界面按钮那条**不需要你做什么**，告诉用户去哪里点就行：
它会问两个问题（给朋友看的名字、装完在哪能看到），然后浏览器直接把 zip 下到下载目录。

⚠️ 按钮走的是宿主路由，**改过插件代码后需要重启 DSH 才生效**；
如果用户点了没反应或报 404，先让他重启。

### 一条命令

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8
node "$env:DSH_HOME\skills\dsh-plugin-submit\tools\export.mjs" `
     "<插件目录>" `
     --name "<给朋友看的名字>" `
     --where "<装完在哪能看到效果>" `
     --out  "<输出目录>"
```

产出一个 `<插件名>-<版本>-分发包.zip`。

### 两个参数要问用户

| 参数 | 为什么要问 | 举例 |
|---|---|---|
| `--name` | 这是**装在朋友机器上、他看到的界面里**会出现的名字 | `窗口背景` |
| `--where` | 朋友装完会问「东西呢？」——这段文字直接写进安装说明 | `设置 → 通用 → 窗口背景` |

`--where` 写不清楚的话，朋友装完找不到入口，一定会来问你。**尽量具体到点哪里。**

### 包里是什么

```
一键安装.cmd      ← 朋友双击这个（纯 ASCII，因为 cmd.exe 用 OEM 代码页）
一键卸载.cmd
install.ps1       ← 真正干活的（UTF-8 带 BOM，所以中文提示正常显示）
uninstall.ps1
安装说明.txt       ← 给朋友看的，已填好 --name / --where
MANIFEST.json     ← 逐文件 sha256
plugin/           ← 插件本体
```

### 朋友那边的体验

解压 → 双击「一键安装.cmd」→ 看完提示 → **重启 DSH**。

安装脚本会自动：找 DSH 主目录、找 profile、**逐文件核对 sha256**、复制文件、建链接、
登记启动清单（改之前先备份、改完读回验证）、检查有没有「双重挂载」冲突。

### 安装脚本会主动拦下这些坏包（别试图绕过）

| 情况 | 后果如果不拦 |
|---|---|
| 少文件 / 传坏了 | 装上去 DSH 可能起不来 |
| 内容被改过 | 同上，且你不知道装的是什么 |
| `dsh.client` 声明了但 `exports` 里没有 `"./client"` | **DSH 直接起不来**（历史上真发生过） |

所以如果导出前结构检查不过，**先帮用户把插件修好**，不要用别的方式打包绕过。

### 想同时上架

先导出给朋友用，再走上面的投稿流程即可，两者不冲突。

---

## 五、投稿前自检清单

在提醒用户「可以投了」之前，快速核对：

- [ ] `package.json` 的 `version` **高于**市场上已有的版本
- [ ] `exports` 里有 `"./client"`（如果声明了 `dsh.client`）
- [ ] `files` 白名单**包含 `package.json`**（漏了会让安装方直接崩）
- [ ] 没有 `postinstall` 之类的生命周期脚本
- [ ] 没有 `eval` / 子进程 / 读取 `~/.ssh` 之类的行为
- [ ] `README.md` 说清楚**装完之后在哪里看到效果**（用户最容易困惑的点）
- [ ] 建议：在 `package.json` 的 `dsh.capabilities` 里声明能力
      （如 `"fs:write"`、`"env"`、`"network:api.example.com"`）——
      **声明了审核会快很多**，因为审核者不用猜

---

## 六、市场规则速查

| 项 | 规则 |
|---|---|
| 插件名 | 小写字母/数字/`.`/`_`/`-`，以字母或数字开头，≤ 64 字符 |
| 版本号 | 必须是 `x.y.z` 形式 |
| 单包大小 | ≤ 4 MB（实际插件通常 < 200 KB） |
| 分类 | 外观 / 效率 / 集成 / 开发 / 数据 / 其他 |
| 审核 | **全部人工终审**，没有任何东西会自动上架 |
| 市场页 | https://your-market-host/plugins/ |
| 上架后用户怎么装 | 设置 → 插件 → D-STATION 市场 → 可下载 → 安装 |

## 七、这个 Skill 的文件

```
skills/dsh-plugin-submit/
  SKILL.md                    本文件
  tools/submit.mjs            投稿：打包 + 投递
  tools/export.mjs            导出：生成自包含安装包
  tools/validate.mjs          结构检查（防「装上去起不来」）
  tools/audit.mjs             风险扫描（防「装着装着被偷数据」）
  tools/test-export.ps1       分发包的端到端安装测试（36 项）
  tools/templates/            安装包里的脚本模板
      install.ps1.tpl         安装器（含 sha256 校验 + 自洽性闸门）
      uninstall.ps1.tpl       卸载器
      一键安装.cmd.tpl        双击入口（纯 ASCII）
      一键卸载.cmd.tpl
      安装说明.txt.tpl        给朋友看的说明
```

整个 `dsh-plugin-submit\` 目录可以**打包直接发给别人**——对方丢进自己的
`%DSH_HOME%\skills\` 下就能用，不需要装任何依赖（纯 Node + PowerShell，无第三方包）。

### 改模板后必须重跑测试

```powershell
powershell -ExecutionPolicy Bypass -File tools\test-export.ps1
```

它会导出真实包、在**假 DSH 环境**里真装一遍，并故意破坏包（删文件 / 改内容 /
去掉 `exports["./client"]`）确认安装器拦得住。**改完不跑等于没改。**

⚠️ 模板文件的两条编码铁律（都是实测踩出来的）：
- **`.ps1` 必须 UTF-8 带 BOM** —— PowerShell 5.1 读无 BOM 的 UTF-8 会当 ANSI，中文乱码且直接语法报错
- **`.cmd` 必须纯 ASCII** —— cmd.exe 用 OEM 代码页读 `.cmd`，中文会乱码
